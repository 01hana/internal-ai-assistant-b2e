## Exact-selection repair

Before repair, `src/query-scope/query-scope-validation.service.ts` selected `active` by **customerId + toolKey only** before looking up a registration. Two distinct activations produced `active.length > 1`, leaving `activation` undefined; a sole activation from another integration could also produce a false policy-unavailable denial. The original acceptance run proved 3/7 PASS, 4/7 FAIL. Existing production policies use distinct tool keys, so this was not evidence that today's C01 was bypassed.

The approved minimal repair first filters activations by trusted Customer + integration + HostApp + toolKey. Only an empty set at this layer returns `NOT_APPLICABLE`. Within an applicable scope it requires exactly one activation matching capability key, binding ID, and Tool version, followed by exactly one matching registration. Missing, duplicate, or drifted exact metadata remains `QUERY_SCOPE_POLICY_UNAVAILABLE`; audit and policy evaluation are unchanged. `evaluatePreCandidate()` shares this selection, while its `ALLOW` result still cannot grant execution. The original seven acceptance cases now pass 7/7 (their correct-policy assertion was strengthened); added cases in the existing validation-unit file pass with correct requestId/messageId audit and foreign-scope isolation.
