# Design: Feature 012 — Grounded LLM Conversation & SSE Streaming

**Canonical Feature Path**: `specs/012-grounded-llm-conversation-sse-streaming`
**Design Date**: 2026-10-02
**Status**: Draft — ready for human approval; implementation not authorized
**Requirements**: `specs/012-grounded-llm-conversation-sse-streaming/spec.md`
**Baseline**: Feature 011 Gate F; pack-backed capability resolution is the sole request-time Tool semantic authority. Feature 011 T078 and Phases G/H/I remain deferred.

## 1. Architecture and Reuse Inventory

The current Backend `AssistantMessageService.sendMessage` completes planning, retrieval/Tool work, grounding, answer decision, persistence, and event construction before `AssistantController` sends the whole SSE array. `AnswerDecisionService.buildAnswerText` and `NoAnswerGateService` supply deterministic answer/safe-failure text. No Assistant request-time path calls `LlmExecutionService.generateAnswer`, `classifyIntent`, or `summarize`. The existing Gateway `GatewayBackendClient.sendStreamMessage` returns a `ReadableStream`; `GatewayAssistantController` forwards chunks with `response.write` and cancels its reader on response close. These are repository observations, not legacy ToolDiscovery assumptions.

| Existing component | V1 disposition | Evidence and bounded change |
| --- | --- | --- |
| `LlmExecutionService` | **EXTEND** | Existing single entry point selects provider and records provider metadata after `generateAnswer`; add abortable bounded generation and streaming through this same service. |
| `LlmProvider` interface | **EXTEND** | Current `generateAnswer`, `classifyIntent`, `summarize` return completed results; add one typed streaming method and signal/limit inputs, retaining current methods. |
| `OpenAiProvider` / Responses client | **EXTEND** | Current Responses `create` returns `output_text` and catches provider errors; use the same injected client/provider, add provider-native incremental output and normalized safe failures. Disable the installed SDK's default retries for generation requests only; do not create another OpenAI client. |
| `LlmModule` and provider selector | **REUSE_AS_IS** | Module exports only `LlmExecutionService`; provider selection already centralizes configured provider. No second registry or selector. |
| LLM configuration | **EXTEND** | Existing `LLM_PROVIDER`, `LLM_MODEL`, `OPENAI_API_KEY` have no generation timeout, output bound, or declared model-context gate. Add bounded server-owned configuration only when implementation is authorized. |
| `LlmObservabilityService` / `AuditWriter` | **EXTEND** | Current provider selected/fallback metadata is append-only but has no stream completion/cancellation/usage outcome. Require an append-only audit attempt for every generation invocation, including failure/cancellation; attempt successful completion audit after core answer commit, with narrow non-blocking handling of audit-only storage failure and a required safe failure signal. Never audit prompt or output text. Predecessor audit semantics stay unchanged. |
| LLM readiness check | **REUSE_AS_IS** for shape; **EXTEND** only if required | Existing dependency check tests provider/model/service presence, not a live provider call. Preserve readiness response contract; do not imply provider availability from configuration alone. |
| Gateway stream forwarding | **REUSE_AS_IS** | Current backend client relays a `ReadableStream` and aborts on cancellation; controller writes each chunk and handles close. Add compatibility tests against Backend incremental output before proposing Gateway edits. |
| `GroundedContextBundleV1` | **WRAP** | Existing assembler validates need/evidence/citation linkage and forbidden authority keys. Create a bounded generation projection above it; never serialize the whole bundle into a prompt. |
| Existing LLM unit and Feature 010 integration tests | **EXTEND** | Retain provider/module/audit tests; deliberately replace only the covered-path zero-generation assertion and add grounded generation/stream/failure coverage. |
| `classifyIntent` / `summarize` | **NOT_USED_IN_V1** | Neither has final-answer authority; Feature 011 remains semantic authority and V1 does not summarize memory. |

No `REPLACE_REQUIRED` classification is justified by current source. There is no existing Assistant grounded-generation prompt builder or provider streaming method to reuse; those are new work **within** the existing LLM boundary, not a reason to duplicate that boundary.

## 2. Authority and Eligibility Decision

Flow:

```text
verified identity + current message
→ Feature 011 scoped capability / Feature 010 follow-up and retrieval routing
→ Feature 008/009 Tool or authorized document retrieval
→ coverage, freshness, conflict, no-answer, risk and approval gates
→ GroundedContextBundleV1
→ deterministic GenerationEligibilityDecision
→ GroundedGenerationContextV1
→ existing LlmExecutionService / provider
→ bounded output and citation validation
→ durable answer finalization
→ existing SSE final
```

The eligibility decision is server-owned and immutable for one answer attempt. It accepts `COMPLETE`, `PARTIAL`, or eligible `CONTEXT_ONLY` **only** with at least one covered evidence need and no blocking gate. It rejects `CLARIFY`, `INSUFFICIENT`, conflict, invalid grounding, no covered lane, risk/approval/confirmation/escalation, and permission-only denial. A denied Tool lane does not block an independently covered Document lane; its `PARTIAL` answer is explicitly limited to the covered part. Model input cannot alter eligibility, requested needs, coverage, capability, exact Tool version/arguments, Customer policy, or permission. No `classifyIntent` call is added.

The existing deterministic clarification and no-answer services remain the single owner of non-eligible outcomes. For eligible success, natural-language generation supersedes only `AnswerDecisionService.buildAnswerText`'s fixed grounded-answer wording; GroundingCheck, AnswerDecision status, citation/evidence linkage, and safe-failure decisions remain server-owned. This is the explicit Feature 010 predecessor amendment: replace the covered-path `generateAnswer` count of zero with **exactly one eligible generation attempt**, while preserving zero LLM semantic/authorization/coverage authority and zero factual generation for blocked outcomes.

## 3. Generation Projection and Trust Classes

`GroundedGenerationContextV1` is an internal, closed, immutable, generation-only value. It contains a trusted eligibility/coverage summary, current question as `UNTRUSTED_USER_TEXT`, up to four bounded same-scope completed exchanges, selected document passages as `UNTRUSTED_DOCUMENT_EVIDENCE`, selected server-projected Tool facts as `SERVER_PROJECTED_TOOL_EVIDENCE`, and an exact citation/evidence allowlist. Prior assistant final text is `COMPLETED_ASSISTANT_TEXT`: useful conversational data, never factual evidence or an instruction authority. It cannot independently create coverage or override current freshness, authorization, or capability decisions. If prior text says inventory is 100 while current approved Tool evidence says 80, the answer must use 80. No raw Tool result, Connector context, credentials, tokens, permissions, internal routing plans, or policy snapshots are projected.

Projection is separate from `ConversationContextLoaderService`, which continues serving semantic follow-up and prior-evidence checks. The generation projector uses the existing verified Customer/session/organization/HostApp/actor scope and additionally requires current integration compatibility for capability-derived context. It reads prior assistant text only when the exchange is durably complete; excludes placeholder, failed/cancelled/partial output; applies the existing source guard to each text; and admits only current-request-revalidated EvidenceRefs. The current bundle's `boundedRecentTurns` does not itself contain prior assistant answer text and must not be mistaken for this new projection.

V1 default input caps are **4 exchanges, 16 KiB serialized UTF-8 context, and 16,384 conservative estimated input tokens**, with stricter server/model configuration allowed but never larger without review. Allocate at most 2 KiB for current user text, 4 KiB for all prior exchange text, 6 KiB for authorized document passages, 3 KiB for projected Tool facts, and 1 KiB for trusted framing/coverage/citation metadata. The token estimate is fail-closed and conservative: count at least one token per UTF-8 byte, making the byte cap the effective universal upper bound until a provider-specific tokenizer is reviewed. Preserve the current question and provenance first; choose current evidence by requested-need order then stable evidence ID; include prior exchanges newest first for selection but present accepted turns chronologically. Truncate content at Unicode boundaries, never citation IDs or field names; if required metadata or at least one covered-evidence fact cannot fit, do not call the model. An output cap of 4 KiB UTF-8 / 1,024 configured provider output tokens is the V1 planning default. These constants are design defaults, not changes to the existing Feature 010 bundle.

Prompt framing is server-owned and outside all untrusted fields. User/document strings are delimited and labeled as data; a phrase such as “ignore previous instructions” is preserved only as quoted source content. Generation context is not built with `JSON.stringify(GroundedContextBundleV1)`. Citations use only the bundle's deterministic IDs. The finalizer checks output bytes, allowed structure, citation/reference syntax and allowlist membership, source-provenance mapping, and prohibited authority/reference patterns; model-generated or unknown ToolCall/EvidenceRef identity is rejected. Server-owned coverage/outcome never changes, and a `PARTIAL` answer must retain the required server-owned disclosure. These are structural and authority checks, not semantic entailment or a generic unsupported-claim validator. Grounded semantic quality is assessed by the restricted context, prompt contract, fixtures, and adversarial evals; no second model judge is added.

## 4. Two-Checkpoint LLM and SSE Design

**Checkpoint C — non-streaming:** Inject `LlmExecutionService` into one generation orchestration seam after eligibility and projection. Use existing `generateAnswer`, validate bounded content/references, then atomically finalize grounding decision and message before returning the current SSE shape. This is a test checkpoint, not the final V1 transport. A provider `finishReason` other than successful stop, empty result, invalid references, output limit breach, or core completion failure produces no successful grounded final. A Feature 012 audit-only failure after core commit follows the narrow non-blocking rule in §5.

**Checkpoint D — true streaming:** Extend the current provider contract with a typed async chunk stream, normalized terminal metadata, AbortSignal, timeout, and output bound; extend `LlmExecutionService` rather than creating `StreamingLlmService`. The Backend controller/orchestrator forwards provider chunks as provisional `answer_delta` events before provider completion, subject only to incrementally checkable bounds/structure/reference syntax, preserving the existing envelope and monotonic sequence. Tool lifecycle/evidence events are emitted after their real stages, before generation. Keep a bounded private accumulator for complete final validation, never to delay every delta until the full answer exists; do not persist each delta. No local splitting of a completed answer and no automatic retry from the first generation attempt, even before a delta. A malformed chunk or stream error emits only the existing safe error form if the connection remains open; never emits a successful final.

Streamed deltas are provisional display text, not an `answered` decision. Complete structural/reference validation is possible only after accumulation; a later failure terminates with an error and leaves no completed answer, even though already-delivered provisional text cannot be recalled from the client. No deterministic semantic-claim approval is implied by releasing a delta.

The Gateway already forwards backend chunks and propagates consumer cancellation through its stream reader. The design requires focused tests that verify actual incremental timing and abort propagation across Browser/Gateway/Backend before classifying Gateway `REUSE_AS_IS` as accepted. If the current Gateway cannot forward incremental chunks or cancel the Backend for a tested case, stop and request a narrowly scoped design amendment; do not build a second transport. Existing SSE names, envelope, `final` payload, history response, SDK contract, and pre-stream HTTP errors remain unchanged. Post-stream errors follow the already-established safe error event contract; no raw provider exception is exposed.

## 5. Completion, Cancellation, and Persistence

The user message remains persisted before planning. A pending assistant row may remain, but it is **not** a completed exchange. Current source creates `Pending answer.` and then creates GroundingCheck/AnswerDecision before separately updating the assistant row; the conversation loader currently uses AnswerDecision presence as its completion test, while public history can read the pending row. That ordering is insufficient for Feature 012 without tightening.

V1 design uses the existing schema with a single scoped transaction for the successful generation's GroundingCheck, AnswerDecision, and assistant final-content update. The generation path creates its AnswerDecision only after provider completion and full output validation. Before commit, disconnect/abort, timeout, provider error, failed validation, or database failure leaves no completed assistant decision. The context repository must require both the decision and a non-placeholder completed final answer; public history must hide or safely represent pending rows without changing its response shape. Successful `final` is emitted only after core commit; the subsequent Feature 012 generation/completion audit is attempted before `final` but an audit-only append failure does not revoke the completed answer or block `final`. If the connection closes **after** durable commit but before the client receives `final`, the answer remains a completed historical result; that is transport-delivery ambiguity, not a cancelled generation. The client can recover through the existing history endpoint. This race cannot be eliminated by claiming that SSE delivery and database commit are one atomic transaction.

No automatic generation retry is allowed at Assistant, `LlmExecutionService`, provider-wrapper, or SDK/client level from the first attempt, before or after a delta. The installed OpenAI SDK defaults to two retries; generation requests must explicitly use `maxRetries: 0` and tests must prove one provider request on failure/timeout. Other existing LLM methods are outside this V1 generation rule. A repeated client POST is a new turn under the current public contract; `requestId` is indexed but not unique on `AssistantMessage`, so exactly-once retry semantics must not be promised. A same-requestId duplicate must not be silently treated as one completed message without a proven idempotency mechanism. If implementation testing shows the existing schema/transaction boundaries cannot reliably distinguish completed from incomplete attempts, set `PRISMA_SCHEMA_DECISION_REQUIRED`, stop before implementation, and seek human authorization; no migration is implicitly approved.

Cancellation chain: HTTP response close → Backend abort controller → generation orchestration → `LlmExecutionService` → provider → OpenAI request. Apply a server-owned deadline and output cap; classify provider error, timeout, abort, malformed chunk, empty output, core commit failure, and post-commit Feature 012 audit-only failure with bounded reason codes. Every LLM invocation requires an append-only audit attempt through the existing writer: failed/cancelled generation is attempted at its terminal outcome, and successful read-only completion is attempted after core answer commit. Use verified Customer scope and request/session/message IDs, provider/model, duration, usage if safely available, outcome, and counts only. Never audit prompt/output text, tokens, keys, raw provider responses, Connector context, or business data. On any append failure, use the existing safe structured logger/telemetry with a fixed reason code, bounded correlation metadata, and `AUDIT_PERSISTED=NO`; never log arbitrary exception text or treat this as a successful append-only audit. Only a post-commit audit-only failure of an otherwise safely completed read-only answer is non-blocking. The minimum safe failure signal is a required acceptance condition. If no such signal can be provided, stop Feature 012 implementation acceptance; `DEFERRED_FEATURE012_AUDIT_OBSERVABILITY_DEBT` may track only enhancements beyond that minimum. A failed or cancelled attempt before commit does not create a successful `final` or reusable assistant answer. This policy applies only to Feature 012 generation/completion observability; Feature 008–011 audit gates remain fail closed, and future write-operation audit policy is undefined.

## 6. Constitution and Compatibility Check

**Before design**: C1 reuses the existing LLM/Gateway boundaries; C2 requires failure/isolation regressions; C3 keeps verified Customer identity out of prompts as authority; C4 keeps public SSE/history compatible; C5 preserves evidence and no-answer gates; C6 (constitution 3.0.0) requires an append-only audit attempt for every LLM invocation and a safely observable post-completion read-only storage failure, while preserving predecessor fail-closed gates; C7 leaves risk/approval deterministic.

**After design**: The projection, eligibility gate, incremental transport, and atomic finalization preserve C1–C5 and C7. The universal audit attempt, required bounded operational failure signal, `AUDIT_PERSISTED=NO`, and unchanged Feature 008–011 gates align this design with amended C6; telemetry is never append-only audit success. This is documentation alignment, not proof of implementation. Separately, the existing schema must support reliable completion under failure; a proved failure triggers `PRISMA_SCHEMA_DECISION_REQUIRED`, not a silent migration.

Feature 011 G/H/I, ToolDiscovery file retirement, the Feature 010 pre-existing `5/6` manifest-hash caveat, keyword RAG, oversized `AssistantMessageService`, `lastMessageAt`, process-local Connector binding, and frontend/UAT debt are `DEFERRED_NON_FEATURE012_DEBT` unless a focused Feature 012 safety test proves direct impact. No Feature 009 T126–T142 task or real Customer request is part of this design.
